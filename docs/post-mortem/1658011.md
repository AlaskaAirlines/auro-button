# AB#1658011

## Executive Summary

Editors, documentation sites and AI tools learn what `auro-button` can do from a machine-generated catalog of its settings, called the manifest. This work makes that catalog accurate and keeps it accurate. Every build now checks the catalog against the design system's rules and fails if it finds a problem. The catalog no longer lists internal settings or theme-wide values as button options. It now groups each option by purpose and notes when an option applies. The descriptions were rewritten for engineers, designers and product leaders.

Fixing the catalog surfaced three real bugs, which are also fixed here:

- Buttons lost their shape and some accessibility information when they switched between button, link and static modes.
- Screen readers kept announcing an old label after an icon button's label changed.
- A `value` setting looked like it worked but never reached the form, so it was removed. This is a breaking change.

See [AB#1658011](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1658011).

## The Problem

The published manifest for `auro-button` happened to pass the design system's quality check, but nothing kept it that way. Any later change could quietly make it wrong, and editors and AI tools would then give consumers bad suggestions. A close look showed it was already misleading in several ways:

- It offered internal-only settings as button options.
- It listed about 60 global theme values as if they were button styling options.
- It described one numeric setting as text.
- It didn't show which options belong together or when they apply.

The manifest was also being generated twice from two different configurations. As a result, the API docs didn't always match what was published.

## Root Cause

- **Nothing enforced the check, and there were two manifest configurations.** `package.json`'s `build` ran `auro build` and then a separate `analyze` script that read the repo's own `custom-elements-manifest.config.mjs`. `auro build` always analyzes with auro-cli's bundled config, so the analyzer ran twice. `docs/api.md` came from one manifest while a different one was published. Nothing ran `auro cem-check`.
- **Internal API leaked into the manifest.**
  - `auro-button` overrides `layout` as private. However, when the analyzer merges an override, the base class's privacy wins and the base class's `layout` attribute is copied in (`src/layoutElement/auroElement.js`).
  - `buttonHref`, `buttonTarget` and `buttonRel` exist only for auro-hyperlink's CTA links, but they weren't tagged as internal.
- **The CSS custom property list was too broad.** The `@cssprop` tags listed all 61 custom properties the styles read. This included global `--ds-size-*` and `--ds-advanced-color-*` tokens, and `--ds-auro-icon-size`, which the button sets on slotted icons rather than accepting as an input.
- **Some types and defaults were wrong.**
  - `tIndex` was typed `String`, though it feeds an integer `tabindex`.
  - `loadingText`'s default was applied as `this.loadingText || "Loading..."` at render time, where the analyzer can't see it.
  - String `@default` values weren't quoted.
- **There was no metadata on grouping or when options apply.** Nothing told tooling which options are UI, behavior or a11y, or that `loadingText` only matters while loading.
- **Bugs surfaced during the audit:**
  - **Rendered element swap.** `src/auro-button.js` renders a `<button>`, an `<a>` or a `<span>` depending on `buttonhref` and `static`. When either changed after the first render, Lit replaced the element. `AuroElement` kept its `wrapper` reference, shape classes and attribute watcher on the removed element, so the new element had no height, padding or radius and no transported ARIA attributes. Separately, `disconnectedCallback()` tore down the transport and nothing re-created it on reconnect.
  - **Stale accessible name.** The `ariaLabel` slots were bound with `@slotchange="${this.requestUpdate}"`. Lit then called `requestUpdate(event)` with the Event as the property name, decided nothing had changed, and skipped the update. Also, `slotchange` doesn't fire when the text inside an already-slotted element changes.
  - **Dead `value` property.** `value` was bound to the inner `<button>`, but the component submits with `requestSubmit()` without a submitter, and auro-form excludes buttons from its form state. The value never reached any form.

## The Fix

- **Build:**
  - Removed `custom-elements-manifest.config.mjs` and the `analyze` script.
  - Added `"cem:check": "auro cem-check --strict"` and changed `build` to `auro build && npm run cem:check`, so a failed check fails the build.
  - Pointed `@aurodesignsystem/auro-cli` at a local tarball build (`file:../auro-cli/aurodesignsystem-auro-cli-0.0.0.tgz`) that ships the CEM plugins in its bundled config. **This is temporary until that auro-cli release is published.**
  - Bumped `auro-library` to ^5.14.4, `auro-loader` to ^6.3.0 and `design-tokens` to ^9.4.1.
- **Manifest hygiene:**
  - Marked `layout` `@private` in `AuroElement` and added `@forcePrivate {'layout'}` to the class.
  - Tagged `buttonHref`, `buttonTarget` and `buttonRel` `@internal`, and stopped documenting the `link` CSS part.
  - Reduced `@cssprop` to the 7 `--ds-auro-button-*` properties the component defines.
- **Metadata:**
  - Added `@category` (`ui`, `behavior` or `a11y`) to each public property.
  - Added `@relevantWhen` to `loadingText`, `tIndex` and `tabindex`.
  - Added inline `{@requiredWhen}`, `{@relevantWhen}` and `{@category}` tags to the slots. auro-cli's plugins turn these into manifest fields.
- **Types and defaults:**
  - `tIndex` is now `Number` with `@minimum -1` and `@maximum 2147483647`. The render fallback is now `this.tIndex ?? this.tabindex` instead of `||`.
  - `loadingText` is set to `"Loading..."` in the constructor, with a matching `@default`.
  - String defaults are now quoted.
- **Deprecation:** marked `tabindex` `@deprecated` in favor of `tIndex`. Its behavior is unchanged.
- **Descriptions:** rewrote the JSDoc descriptions that feed the manifest, editor tooltips and the API docs. Corrected `transportAttributes`' JSDoc, which listed a nonexistent `observe` parameter, left out `match`, and gave the wrong return type.
- **Bug fixes:**
  - `AuroElement` now calls `bindWrapper()` after every update. It re-queries `.wrapper` and, when the element changed, re-points `wrapper` and the attribute watcher and re-applies the shape and layout classes. `releaseWrapper()` first returns transported attributes to the host. `disconnectedCallback()` and `connectedCallback()` use the same release/bind pair.
  - The `ariaLabel` slots now call `onAriaLabelSlotChange()`, which calls `requestUpdate()` with no arguments. A `MutationObserver` on the host's light DOM re-renders when the text inside a slotted label element changes.
  - Removed the `value` property, its template binding and its test (`feat!`).
- **Build hygiene:**
  - Replaced `/` division and the global `call()` and `type-of()` with `sass:math` and `sass:meta` functions.
  - Dropped the deprecated, unused `insetUtility` mixin.
  - Reordered declarations to satisfy Stylelint's `order/properties-order`.
- **Tests:** added 8 tests in `test/auro-button.test.js`:
  - Rendered-element swaps for `static` set and removed and for `buttonhref` set.
  - ARIA attributes added after a swap.
  - `ariaLabel` slot content replaced and its text changed, including the loading label.
  - ARIA transport after the element is removed and re-inserted.

## Why This Works

- **One manifest.** With only `auro build`'s analysis left, the published `custom-elements.json` and `docs/api.md` come from the same manifest. Chaining `cem:check` with `&&` means any non-zero exit fails `npm run build`, so regressions get caught.
- **Privacy is enforced.** `@forcePrivate` overrides the analyzer's merge behavior, where the base class's privacy wins. `@internal` removes the CTA-only fields once auro-cli's internal plugin runs. Limiting `@cssprop` to `--ds-auro-button-*` matches what `cssProperties` means: the component's own styling API.
- **`??` is required, not cosmetic.** As a `Number`, `tIndex="0"` becomes `0`, which `||` would treat as empty and skip. `??` falls back only when the value is `null` (Lit's Number converter when the attribute is removed) or `undefined`.
- **The constructor default is behavior-neutral.** Lit restores properties set before upgrade after the constructor runs, and applies attributes later still. Consumer values still win, and the analyzer can now read the default.
- **Re-binding after each update works for any element swap.** It handles every case where Lit replaces the rendered tag, not just the known `static` and `buttonhref` paths. Returning attributes to the host before re-binding means the new watcher moves them across exactly as on first render.
- **Calling `requestUpdate()` with no arguments always schedules a render**, and the `MutationObserver` covers how React, Vue and Lit usually update a label: by changing the text of an existing node.
- **The Sass and Stylelint changes don't change the compiled CSS**, apart from removing the unused `.util_inset*` classes. Declarations that overlap, such as shorthands and their longhands, keep their relative order.

## Outcome

- `auro-button`'s published manifest passes the design system's strict check with no errors or warnings, and the build now stops if that changes.
- Editors, docs and AI tools see only the button's real options. Each option is grouped by purpose and marked with when it applies.
- The descriptions explain what each option is for and when to use it.
- The published API docs now match the published manifest.
- Buttons keep their shape and accessibility information when they switch between button, link and static modes.
- Screen readers announce the current label on icon-only buttons.
- The build no longer prints Sass deprecation warnings or Stylelint errors.
- All 36 automated tests pass.
- **Breaking change:** the non-working `value` setting is gone. Teams that read it should use a `data-*` attribute instead.

## Learnings

- `auro build` always analyzes with auro-cli's bundled config. A repo-owned `custom-elements-manifest.config.mjs` plus a separate `analyze` step doesn't replace that: it adds a second, divergent manifest. Put CEM plugins in auro-cli's bundled config instead.
- When the analyzer merges an inherited member, the base class's privacy wins over the subclass override. Use `@forcePrivate` on the class, or mark the member private at its source.
- `@cssprop` should list only the component's own `--ds-auro-<component>-*` properties. Global tokens the styles happen to read aren't part of the component's API.
- Changing a property from `String` to `Number` can break `||` fallbacks, because `0` is falsy. Use `??`.
- Set defaults in the constructor, not as `x || default` at render time, so the analyzer can record them. Lit's upgrade order keeps consumer values winning.
- Never bind `@slotchange="${this.requestUpdate}"`. Lit passes the Event as the property name and skips the update. Wrap it in a method that calls `requestUpdate()` with no arguments. `slotchange` also doesn't fire for text changes inside a slotted element.
- Any component that renders a different tag based on a property must re-bind references, classes and observers after Lit replaces the element. A one-time bind in `firstUpdated` isn't enough.
- Custom JSDoc tags such as `@minimum`, `@relevantWhen` and `@category` do reach `custom-elements.json`, but the generated `docs/api.md` table has no columns for them. Check the manifest itself, not the API docs, to confirm they're there.
- An audit of the manifest is a useful bug hunt. Reviewing each property's real behavior found the dead `value` property and two accessibility bugs.

## Iterations That Didn't Work

- **A repo-owned CEM config (from AB#1633055).** The earlier ticket added `custom-elements-manifest.config.mjs` and an `analyze` script so the repo controlled its own manifest. That made `auro build` and `analyze` produce two different manifests, and `docs/api.md` didn't match what was published. This work reverses it and moves the plugins into auro-cli's bundled config.
- **`@private` on the subclass override of `layout`.** The analyzer ignored it: the base class's privacy won the merge, and the base class's `layout` attribute was still copied in. Hiding `layout` required `@private` at the source in `AuroElement` plus `@forcePrivate {'layout'}` on the class.
